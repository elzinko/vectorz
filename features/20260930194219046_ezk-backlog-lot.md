# 20260930194219046 — ezk-backlog : concept de lot (sprint backlog) + définition d'incrément

## En clair

C'est la **fondation** du nouveau cycle. Aujourd'hui `ezk-backlog` sait tirer **une** fiche
(`next`). Il lui manque de **sélectionner et figer un lot de N fiches** ready — le « sprint
backlog » — et de dire ce qu'est l'**incrément** que ce lot produit. Sans cette brique, les verbes
`start`/`close` (fiche 2) resteraient au niveau *feature* et `close` retomberait à 1×/feature :
le problème d'origine.

## Contexte / Problème

Le panel adverse du 2026-09-30 (architecte + PO) a tranché : le vrai manque n'est **pas** les
verbes, c'est **le lot**. `plan`/`next`/`groom` couvrent déjà l'ordre, le grooming et le tirage
d'**une** fiche. Sélectionner/figer **un lot de N fiches ready** est une capacité **neuve** ; par
responsabilité unique, elle vit dans **`ezk-backlog`** (le « quoi »), **jamais** réimplémentée dans
`ezk-sprint`. Voir [ADR-0054](../products/mega-city/docs/adr/0054-cloture-sprint-vs-archive-session.md).

## Proposition

- **Notion de lot** dans `ezk-backlog` : sélectionner N fiches **ready** (non-épic), dans l'ordre
  priorité/PLAN, et les **figer** comme sprint backlog courant (ex. `next --lot N`).
- **Porté par `SPRINT.md` + un pointeur** (liste d'ids/PRs du lot). **Pas** d'objet « sprint »
  persistant — YAGNI : l'incrément existe déjà (commits squash sur `main` + fiches `shipped`).
  C'est la décision **(a)** de l'ADR-0054.
- **Définition de l'incrément** (par doc) : l'incrément d'un sprint = l'ensemble des fiches
  **shipped** du lot (leurs squash-merges). Aucun nouvel artefact.
- `ezk-sprint start` (fiche 2) **consomme** ce lot ; il ne le construit pas.

## Critères d'acceptation

- [ ] `ezk-backlog` sélectionne un **lot de N fiches ready** (non-épic), dans l'ordre priorité/PLAN, et le fige (`SPRINT.md` + pointeur).
- [ ] La sélection respecte les règles existantes : ready-only, **tête bloquée** signalée, **aucune inversion de priorité** silencieuse.
- [ ] L'**incrément** est défini par doc : lot livré = fiches `shipped` du lot ; **aucun** objet persistant en plus.
- [ ] **Zéro régression** sur `next` / `plan` / `groom` (tests verts).
- [ ] `SKILL.md` d'`ezk-backlog` documente **lot** + **incrément** ; des tests couvrent la sélection de lot.

## Comment vérifier

```bash
pnpm --dir products/mega-city test
pnpm --dir products/mega-city test:scripts
# + revue : sélectionner un lot de N fiches ready et vérifier le figeage (SPRINT.md + pointeur)
```

## Notes / décisions

- **Fondation** du cycle de vie — construite **en premier** (fiches 2 et 3 en dépendent).
- Re-scope du 2026-09-30 (Option A tranchée par le PO) : fiche 2 = [`ezk-sprint start/close`](20260930123438875_cycle-vie-sprint-session-ceremonies.md) · fiche 3 = [`ezk-product-build` orchestrateur de session](20260930194219068_ezk-product-build-orchestrateur-session.md).
- Décisions ADR-0054 portées ici : **(a)** pas d'objet sprint persistant · **(b)** le lot vit dans `ezk-backlog`, pas dans `ezk-sprint start`.
