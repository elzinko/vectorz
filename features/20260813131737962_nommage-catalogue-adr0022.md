# Nommage & catalogue de la méthode

## En clair

Trois préfixes se baladent pour 23 skills (`ezk-`, `supervision-`, `vz-`), `ezk-pr-pilot` garde
un `-pilot` que l'ADR-0022 veut mort, et le README range 3 skills **hors** de sa table scannable.
Résultat : un nouvel arrivant ne sait pas *qui existe* ni *quel nom fait loi*. On aligne tout sur
la carte ADR-0022.

## Contexte / Problème (findings audit 2026-08-13)

- 🟡 `products/mega-city/skills/ezk-pr-pilot/SKILL.md:2` (+ dossier, `skills/README.md:34`) —
  toujours `-pilot`, alors qu'ADR-0022 (l.52) acte `ezk-pr`. Dette assumée (`ezk-pr-pilot/SKILL.md:24`)
  jamais exécutée.
- 🟡 `products/mega-city/docs/adr/0022-*.md` — la carte ne prévoit **aucune bande/préfixe** pour
  `supervision-*` (2 skills, vrai sous-domaine) ni `vz-*` (1 skill, préfixe orphelin).
- 🟡 `products/mega-city/skills/README.md:44` — `supervision-demo`, `supervision-analyze`,
  `vz-product-builder` n'existent que dans une **note en prose**, absents de la table (sans état/rôle).
- 🟡 `skills/README.md:21-40` — l'axe « état » est de l'**archéologie de migration**
  (`📥 importé`, `📦 récupéré`…), pas un statut lisible (ready / experimental / deprecated).

## Proposition

1. **Renommer `ezk-pr-pilot` → `ezk-pr`** — déplacer le **dossier complet** (`git mv` ; il porte
   `assets/` + `scripts/`, donc **pas** via `ezk-ezk deploy` qui ne copie que `SKILL.md`), mettre à jour
   `name:` + toutes les réf + l'entrée de catalogue, et **re-bind** les profils.
   **Contrainte de sortie** (mécanisme exact à instruire au grooming/impl.) : **0 résidu, sans risque**.
   Le re-bind seul **ne nettoie pas** l'ancienne entrée globale — `applyGlobalPlan` n'itère que le
   *nouveau* plan (`src/io/apply.ts:296-335`) et le défaut est `copy` (apply.ts:301), donc l'entrée
   `~/.claude/skills/ezk-pr-pilot` subsiste (un **dossier** en copy, un **symlink** en link). Il faut la
   retirer, mais par un **retrait GARDÉ** — vérifier qu'elle est bien *gérée* (même invariant
   d'appartenance que `assertReplaceableSkillDir`) ; **jamais** un `rm -rf` aveugle (détruirait une perso
   utilisateur) **ni** une purge globale des entrées hors-plan (effacerait des skills omis exprès, ex.
   `daily`). Option propre : **durcir le binder** pour gérer proprement les renommages.
2. **Étendre ADR-0022** : ranger la famille `supervision-*` (capacité diagnostic + banc jouet) et
   **classer `vz-*`** dans la carte — **sans rouvrir** la décision overlay déjà prise par le PO
   ([0164](0164-vz-product-builder-corpus-reviewers.md), in-progress) ; au plus un renommage
   cosmétique `ezk-*` si le PO le décide, **jamais un fold-in**.
3. **README catalogue — réconciliation COMPLÈTE avec le disque + `profiles/*.yml`** (pas juste la
   table) : (a) table scannable des 23 skills — **axe Statut unique** (ready|experimental|deprecated)
   + colonne provenance ; (b) **totaux agents/skills exacts** — aujourd'hui périmés : le résumé dit
   « 6 agents / 19 skills » alors que `global.yml` en liste **7 / 20** (`ezk-archive` manquant) ; (c)
   **0 réf `install.sh`** et **réf de fiches à jour** (rot : `vz` = 0164, pas 0060…). Filet : le test
   `catalog-readme.test.ts`.

## Critères d'acceptation (brouillon — DoR au grooming)

- [ ] `ezk-pr-pilot` renommé `ezk-pr` (0 réf résiduelle à `-pilot`).
- [ ] ADR-0022 classe explicitement `supervision-*` et le **classement** de `vz-*` (sans rouvrir la décision overlay de [0164](0164-vz-product-builder-corpus-reviewers.md)).
- [ ] Le README catalogue est **cohérent avec le disque et `profiles/*.yml`** : 23 skills tabulés +
      statut lisible, **totaux agents/skills exacts** (7/20), 0 réf `install.sh`, réf de fiches à jour.
