## Ta question — faut-il que `ezk-product-build` fonctionne comme ça à chaque fois ?

**Presque tout y est déjà** comme réglage : `--mode auto` (autonome), `--retro` (rétro entre
itérations), auto-groom jusqu'à la DoR, saut des fiches `blocked:`, RUN-REPORT qui liste les
sautées. **Trois manques** (dont un touche un garde-fou voulu — le tag réservé au PO) sont fichés
dans [20261011103839682](../../features/20261011103839682_product-build-run-multi-versions-regles.md) :
dérouler plusieurs versions avec rétro+tag par version, l'auto-tag/close local en opt-in (via un
ADR), et sortir une fiche de sa version quand elle est inconstruisable. À trancher par toi.

## Tokens & méthode

Mode `lean` : zéro fan-out multi-agents, construction **inline** (le contexte de run signalait qu'un
sous-agent lancé dans ce worktree écrirait dans son propre worktree). Gate complète (`test` +
`test:scripts` + typecheck + biome + link-checker) **jouée et verte sur chaque fiche**. Revue adverse
tenue (lean : self-review sur petits patchs additifs). `ezk run report` non utilisé : il refuse une
livraison locale sans numéro de PR (lacune déjà connue).

## Incident git — merge manuel

Une **autre session** a laissé un fichier non suivi (`docs/captures/2026-10-11-retro-outillage-…md`)
dans le checkout principal partagé. `ship-merge --local` refuse tout arbre « sale », même un fichier
non suivi → j'ai fait les derniers squash-merges **à la main** (`git merge --squash` + commit), qui
n'embarquent jamais un fichier non suivi. Le fichier de l'autre session est resté intact. C'est une
des deux frictions de la [rétro v0.9](../../features/20261011112934507_retro-v09-ship-merge-untracked-et-rayon-fiches.md).
